# ルールJSONエクスポート機能 E2Eテスト戦略

## 目的

ブラウザ拡張機能としてのエクスポート機能のエンドツーエンドテストを定義する。
エクスポートボタンのクリックからJSONファイルのダウンロード完了までの一連のフローを検証する。

## テストスコープ

### 対象フロー

1. ユーザーがポップアップからルールを保存する
2. ルール一覧ページを開く
3. エクスポートボタンをクリック
4. JSONファイルがダウンロードされる
5. ダウンロードされたファイルの名前とJSON内容が正しい

### 対象ページ

| ページ | URL | 役割 |
|-------|-----|------|
| ルール一覧 | `chrome-extension://{id}/rules.html` | エクスポート操作 |
| ポップアップ | `chrome-extension://{id}/popup.html` | テストデータ（ルール）作成 |
| テストページ | `http://localhost:8080/agile-manifesto.html` | URL取得用 |

### 検証ポイント

| 観点 | 検証内容 | 検証方法 |
|------|---------|---------|
| UI状態変化 | エクスポートボタンが表示されクリック可能 | ボタンが存在しdisabledでないことを確認 |
| ファイルダウンロード | JSONファイルがダウンロードされる | Playwright `download` イベントで取得 |
| ファイル名 | 命名規則に従ったファイル名 | `frog-frame-front-rules-YYYYMMDD_hhmmss.json` パターンで一致確認 |
| JSONフォーマット | version, exportedAt, rulesを含む正しい構造 | ダウンロードファイルをパースして検証 |
| ルールデータ | エクスポートしたルールに登録済みルールが含まれる | rulesフィールドを検証 |
| コンソールエラー | エラーが発生しないこと | `page.on('console')` で監視 |

## テスト分類

### 1. 正常操作フロー - エクスポート実行とJSONダウンロード

エクスポートボタンクリックからJSONファイルダウンロードまでの基本フローを検証する。
今回の機能の最重要シナリオであり、UIからDB（IndexedDB）永続化データの読み出しまでの全フローをカバーする。

| 分類 | テストケース | 根拠 |
|------|-------------|------|
| 基本エクスポートフロー | エクスポートボタンクリック後にJSONファイルがダウンロードされる | ユーザー視点での基本操作を確認 |
| ファイル名検証 | ダウンロードファイル名が命名規則（`frog-frame-front-rules-YYYYMMDD_hhmmss.json`）に従う | 00-overview.md「ファイル命名」要件 |
| JSONフォーマット検証 | ダウンロードしたJSONにversion, exportedAt, rulesが含まれる | 00-overview.md「JSONフォーマット」要件 |
| ルールデータ検証 | エクスポートしたJSONのrulesに登録済みルールが全件含まれる | バックアップ・リストア用途の確認 |

**対応テスト**: `normal-flow.spec.ts`

## ユーザーストーリートレーサビリティ

| 受け入れ条件 | テストケース | テストファイル |
|-------------|-------------|---------------|
| AC-1: エクスポートボタン表示 | ルール1件以上の場合、エクスポートボタンが有効化 | normal-flow.spec.ts |
| AC-2: JSONファイルダウンロード | ボタンクリックでJSONファイルがダウンロードされる | normal-flow.spec.ts |
| AC-3: ファイル名形式 | ダウンロードファイル名が命名規則に従う | normal-flow.spec.ts |
| AC-4: JSONフォーマット | JSON内容にversion, exportedAt, rulesが含まれる | normal-flow.spec.ts |
| AC-5: ルール0件時ボタン無効化 | E2E対象外（結合テストでカバー） | - |
| AC-6: 重複実行防止 | E2E対象外（結合テストでカバー） | - |
| AC-7: エラー通知 | E2E対象外（結合テストでカバー） | - |
| AC-8: Clean Architecture準拠 | E2E対象外（コードレビューで検証） | - |

### E2E検証困難な項目の理由

| 受け入れ条件 | E2E検証が困難な理由 |
|-------------|-------------------|
| AC-5: ルール0件時ボタン無効化 | ルール0件状態を作ってUIを検証すること自体は可能だが、ボタン無効化はUIの単体レベルで確認できるため結合テストが適切 |
| AC-6: 重複実行防止 | エクスポート処理中の状態を再現するにはタイミング制御が必要で、E2Eでは安定した検証が困難 |
| AC-7: エラー通知 | エラーを発生させるにはAPIモックが必要だが、E2Eでは実際の環境を使用するため技術的に困難 |
| AC-8: Clean Architecture準拠 | コードレビューおよびLintルール（ESLint/clean-architecture）で検証する |
