# アサーションルール

E2Eテストでのアサーション（検証）に関するルール。

---

## ヘルパー関数使用時の重複アサーション禁止

### 規約

- アサーションを含むヘルパー関数を使用した後、同じ検証を重複して行わないこと
- ヘルパー関数の内部実装を信頼する

### 禁止事項

- ヘルパー関数が既に行っている検証と同じ内容を再度アサーションすること
  - テストコードが冗長になり、保守性が低下する

### 適用シナリオ

- ルール件数を検証するヘルパー関数（例: `waitForRuleCount`）を呼び出した後に、同じ件数を再度`getRuleCount` + `expect`で検証するのは冗長であるため行わない
- ダイアログ待機ヘルパーが内部で可視性検証を行っている場合、呼び出し後に再度`toBeVisible()`を実行しない

### eslint-rule

ESLint化不可（ヘルパー関数の内部実装との重複はコード静的解析では判定困難。PRレビューで確認）

## 検索・取得結果の前提条件検証

### 規約

- インデックスや要素を検索・取得するヘルパー関数を使用した後、その結果が期待通りであることを明示的に検証すること
- 前提条件が満たされない場合に明確な失敗メッセージを出すことで、デバッグを容易にする

### 対象となるパターン

| 戻り値の型 | 検証方法 |
|-----------|---------|
| インデックス（-1が失敗を示す） | `expect(index).toBeGreaterThanOrEqual(0)` |
| nullable値（null/undefinedが失敗を示す） | `expect(value).toBeDefined()` または `expect(value).not.toBeNull()` |
| 配列（空が失敗を示す） | `expect(array.length).toBeGreaterThan(0)` |

### 適用シナリオ

- 特定のoldStringを持つルールのインデックスを取得した後、そのインデックスを使って削除ボタンをクリックする場合、インデックスが`-1`でないことを事前に検証する。検証しないと、`-1`が渡されたときに「行が見つからない」原因が不明瞭になる
- 要素検索ヘルパーの戻り値をそのまま次の操作に渡す場合、失敗時のエラーメッセージが「期待: >= 0、実際: -1」のように原因を示すよう前提条件を検証する

### eslint-rule

ESLint化不可（ヘルパー関数の戻り値の意味はコード静的解析では判定困難。PRレビューで確認）

## 状態アサーション前の可視性検証

### 規約

`toBeFocused()`、`toBeChecked()`などの**状態依存アサーション**の前に、`toBeVisible()`で要素の可視性を検証すること。

### 理由

- ダイアログやモーダル内のボタンは、コンテナ要素が表示されても個々のボタンの描画が遅れる場合がある
- 状態アサーションが失敗した場合、「要素が見えていないのか」「見えているが状態が違うのか」の切り分けが困難
- 可視性を先に検証することで、失敗原因が明確になりデバッグが容易になる

### 対象となるアサーション

| アサーション | 前提条件 |
|-------------|---------|
| `toBeFocused()` | `toBeVisible()` |
| `toBeChecked()` | `toBeVisible()` |
| `toHaveValue()` | `toBeVisible()` |

### 適用シナリオ

- 確認ダイアログのキャンセルボタンにフォーカスが当たることを検証する場合、先に`toBeVisible()`でボタンの描画完了を確認してから`toBeFocused()`を検証する。描画タイミングの差で失敗した場合に原因を切り分けやすくなる
- フォーカストラップのテストでTab/Shift+Tab後のフォーカス位置を検証する場合も、対象要素の可視性を先に確認する

### eslint-rule

ESLint化不可（アサーションの前提条件はコード静的解析では判定困難。PRレビューで確認）

## ステップコメントとアサーションの一致

### 規約

テストコード内のステップコメント（`// Assert: ...`）は、**実際のアサーションが検証する内容と一致**させること。

テスト名に関する命名規則（[naming-rules.md](./naming-rules.md)）と同じ原則がステップコメントにも適用される。

### 禁止事項

- アサーションの検証範囲を超える表現をコメントに書くこと
  - `toBeEnabled()` のみで検証しているのに「クリック可能」と書くのは不正確
  - 「クリック可能」は `click()` + 結果確認まで含む意味になる

### 適用シナリオ

- `toBeEnabled()` で検証するステップには「enabledである」と記述する。「クリック可能」と書くとオーバーレイ非ブロック等の検証も含意するため不正確
- `toBeVisible()` で検証するステップには「表示される」と記述する。「操作可能」と書くと実際の操作検証も含意するため不正確

### eslint-rule

ESLint化不可（コメントの意味的な正確性はコード静的解析では判定困難。PRレビューで確認）
