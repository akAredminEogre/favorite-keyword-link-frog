# PR運用ポリシー

## 基本方針

**機能PRの境界を守りつつ、軽微な周辺改善・ユーザーストーリーのバックログ登録は同一PRに含めてよい。コード改善（リファクタリング・実装変更）は別PRで対応する。**

## 同一PRに含めてよいもの

| 種別 | 説明 | 例 |
|------|------|-----|
| **バグ修正** | 関連コードのバグを発見した場合 | コメントのtypo修正、不要なconsole.log削除 |
| **ドキュメント改善** | 関連ドキュメントの不備 | 説明が不明瞭な箇所の補足 |
| **テストの補完** | 発見したカバレッジ不足 | 関連ユニットのテスト追加 |
| **ユーザーストーリーの追加** | バックログ登録のみ（着手しない） | `docs/user-stories/` への新規追加のみ、実装なし |

**ユーザーストーリー追加の運用**: 空きエージェントが担当し、実装着手は別PRで行う。

## 同一PRに含めないもの

| 種別 | 対応 |
|------|------|
| **コード改善・リファクタリング** | 別PRで対応 |
| **別機能の実装** | 別PRで対応 |
| **大規模リファクタリング** | 別PRまたはレビュー担当者に相談 |
| **設計変更を伴う改修** | レビュー担当者→プロジェクトオーナーに相談 |

## PRの説明に含めること

同一PRに複数の変更を含める場合、PR説明に明記する:

```markdown
## 主要変更
- [本来のユーザーストーリー対応] xxx機能の実装

## 付随改善
- [気づき] xxx.tsのtypo修正
- [気づき] 未使用importの削除
```

## ブランチ命名

- メイン: `feat/user-story-xxx`（ユーザーストーリー起点）
- ユニット: `feat/unit-xxx`（並行開発時のユニット単位）
- バグ修正: `fix/issue-xxx`
